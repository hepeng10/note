### C语言团队协作编程规范（通用版）
#### 一、核心原则
1. **可读性优先**：代码是写给人看的，其次才是给机器执行；
2. **一致性至上**：团队内所有成员严格遵循同一套规范，避免“个人风格”；
3. **安全性优先**：杜绝内存泄漏、野指针、缓冲区溢出等C语言典型坑；
4. **可维护性**：代码结构清晰，便于后续修改、扩展、调试。

---

#### 二、文件与工程结构规范
（类比JS/TS的模块化、GO的包结构，C语言通过文件/目录划分模块）
##### 1. 目录结构
```
project/
├── src/              # 源代码目录
│   ├── module_a/     # 模块A（比如网络模块）
│   │   ├── a.c       # 实现文件
│   │   └── a.h       # 头文件
│   ├── module_b/     # 模块B（比如存储模块）
│   └── main.c        # 程序入口
├── include/          # 公共头文件（跨模块共享）
├── test/             # 单元测试代码
├── doc/              # 文档（接口说明、设计文档）
├── Makefile          # 编译脚本（或CMakeLists.txt）
└── README.md         # 项目说明
```

##### 2. 文件命名
- 全部小写，单词间用下划线`_`分隔，禁止中文/特殊字符；
- 实现文件：`模块名_功能名.c`（如`net_tcp.c`）；
- 头文件：与实现文件同名（如`net_tcp.h`），禁止不同名；
- 公共头文件：加项目前缀（如`proj_common.h`），避免与系统头文件冲突。

##### 3. 头文件保护（必做）
所有`.h`文件必须加“防止重复包含”的保护，优先用`#pragma once`（简洁），兼容场景用宏定义：
```c
// 方式1：简洁版（主流编译器支持）
#pragma once

// 方式2：兼容版（通用）
#ifndef PROJ_MODULE_A_H  // 宏名：项目名_模块名_H（全大写，下划线分隔）
#define PROJ_MODULE_A_H

// 头文件内容

#endif // PROJ_MODULE_A_H
```

##### 4. 头文件依赖原则
- 头文件只包含“必要的依赖”：仅包含当前头文件需要的类型、宏、函数声明，杜绝“万能头文件”；
- 实现文件（.c）优先包含“自身头文件”：比如`net_tcp.c`第一行必须是`#include "net_tcp.h"`，便于检查头文件完整性；
- 系统头文件与自定义头文件分开，系统头文件在前，用空行分隔：
  ```c
  #include <stdio.h>
  #include <stdlib.h>

  #include "net_tcp.h"
  #include "proj_common.h"
  ```

#### 三、命名规范
（类比GO的“小写私有/大写公有”、JS的驼峰，C语言以“下划线命名法”为核心）
##### 1. 通用规则
- 所有命名必须“见名知意”，禁止拼音/无意义字符（如`a1`/`tmp`/`aaa`）；
- 禁止与系统关键字/库函数重名（如`int printf;`）；
- 长度适中：避免过短（如`n`）或过长（如`network_transmission_control_protocol_flag`）。

##### 2. 具体命名规则
| 类型                | 命名规则                          | 示例                          |
|---------------------|-----------------------------------|-------------------------------|
| 全局变量（公有）| 项目前缀_模块名_变量名（全小写）| `proj_net_tcp_port`           |
| 全局变量（私有）| static + 模块名_变量名（全小写） | `static int net_tcp_timeout;` |
| 局部变量            | 小写+下划线，简洁明了            | `int conn_fd;` `char buf[128];` |
| 常量/宏定义         | 全大写+下划线                     | `#define MAX_BUFFER_SIZE 1024` |
| 枚举类型            | 类型名：大驼峰；枚举值：全大写    | `typedef enum { TCP, UDP } ProtocolType;` |
| 结构体/联合体       | 大驼峰+前缀（可选）| `typedef struct TcpConn { ... } TcpConn;` |
| 函数（公有）| 模块名_功能名（全小写）| `int net_tcp_connect();`      |
| 函数（私有）| static + 模块名_功能名            | `static int net_tcp_check_fd();` |
| 指针变量            | 前缀加p（可选，提升可读性）| `int *p_fd;` `TcpConn *p_conn;` |

##### 3. 禁用示例
```c
// 错误：拼音+无意义
int wangge; 
// 错误：与系统宏冲突
#define NULL 0 
// 错误：全局变量无模块前缀，易冲突
int port = 8080; 
// 错误：函数名大小写混乱
int NetTcp_Connect(); 
```

#### 四、代码格式规范
（统一格式是团队协作的基础，建议配合工具：Clang-Format、VSCode的C/C++插件）
##### 1. 缩进与空格
- 缩进：**4个空格**（禁止用Tab，避免不同编辑器显示不一致）；
- 运算符两侧加空格：`a = b + c;`（而非`a=b+c;`）；
- 逗号后加空格：`func(a, b, c);`（而非`func(a,b,c);`）；
- 花括号`{}`：左括号不换行，右括号单独换行（函数/条件/循环统一）：
  ```c
  // 正确
  if (a > 0) {
      printf("ok\n");
  } else {
      printf("error\n");
  }

  // 函数格式
  int net_tcp_connect(int port) {
      // 函数体
      return 0;
  }
  ```

##### 2. 行长度与换行
- 单行代码不超过80/120字符（团队统一标准），超长时换行：
  ```c
  // 错误：单行过长
  int result = net_tcp_send_data(p_conn, buf, len, timeout, retry_count);
  // 正确：换行（参数对齐）
  int result = net_tcp_send_data(
      p_conn, buf, len, timeout, retry_count);
  ```
- 一行只写一条语句：禁止`if (a>0) printf("ok");`（除非极简单场景）。

##### 3. 空行使用
- 函数之间加1个空行；
- 函数内不同逻辑块之间加1个空行；
- 禁止连续多个空行（除文件末尾可留1行）。

#### 五、语法与安全性规范
（C语言无GC，安全性是重中之重）
##### 1. 变量与常量
- 变量声明：
  - 局部变量在函数开头/使用前声明（禁止混合在代码中）；
  - 所有变量必须初始化（杜绝野值）：`int fd = -1;` `char *p = NULL;`；
- 常量优先用`const`而非宏：`const int MAX_LEN = 1024;`（类型安全）；
- 全局变量慎用：必须用的全局变量加`static`（本文件私有），跨文件共享需在头文件用`extern`声明，且注释用途。

##### 2. 指针操作（核心安全点）
- 所有指针必须初始化（`NULL`）；
- 解引用前必须判空：
  ```c
  // 正确
  if (p != NULL) {
      *p = 10;
  }
  // 错误：直接解引用
  *p = 10;
  ```
- 禁止返回局部变量的指针（栈内存会被回收）：
  ```c
  // 错误
  int *func() {
      int a = 10;
      return &a; // 返回栈指针，野指针！
  }
  // 正确（如需返回，用malloc分配堆内存）
  int *func() {
      int *p = (int*)malloc(sizeof(int));
      if (p != NULL) {
          *p = 10;
      }
      return p;
  }
  ```

##### 3. 内存管理
- 堆内存分配（`malloc/calloc/realloc`）后必须判空：
  ```c
  char *buf = (char*)malloc(1024);
  if (buf == NULL) {
      printf("内存分配失败\n");
      return -1;
  }
  ```
- 内存释放：
  - `free`后必须将指针置`NULL`：`free(buf); buf = NULL;`（避免野指针）；
  - 配对原则：`malloc`和`free`在同一逻辑层级（比如申请后必须在函数退出前释放，或明确传递释放责任）；
  - 禁止重复`free`、禁止`free`栈内存。

##### 4. 条件与循环
- 条件判断：
  - 常量放左侧（避免赋值错误）：`if (NULL == p)`（而非`if (p == NULL)`，写错`=`会编译报错）；
  - 禁止省略花括号（即使单行）：
    ```c
    // 错误：易误加代码导致逻辑错误
    if (a > 0)
        printf("ok\n");
    // 正确
    if (a > 0) {
        printf("ok\n");
    }
    ```
- 循环：
  - 避免死循环（必须有退出条件）；
  - 循环变量尽量局部化：`for (int i = 0; i < 10; i++)`（C99及以上支持）。

##### 5. 函数规范
- 函数设计：
  - 单一职责：一个函数只做一件事，行数控制在50行内；
  - 参数：输入参数加`const`（如`void func(const char *str)`），避免意外修改；
  - 返回值：明确错误码（比如0=成功，-1=失败，正数=具体错误类型），禁止用0表示失败（易与正常返回值混淆）；
- 函数声明：
  - 所有函数必须在头文件/实现文件开头声明（禁止隐式声明）；
  - 私有函数（本文件用）加`static`。

#### 六、注释规范
（注释不是越多越好，关键是“说明为什么，而非做什么”）
##### 1. 注释风格
- 单行注释：`// 注释内容`（优先，简洁）；
- 多行注释：`/* 多行注释 */`（仅用于大段说明）；
- 禁止注释与代码同行（除非极简单）：`int a = 10; // 赋值`（无意义）。

##### 2. 必须加注释的场景
- 文件头部：说明文件用途、作者、修改时间、核心逻辑；
  ```c
  /**
   * @file net_tcp.c
   * @brief TCP通信模块，实现连接、发送、接收功能
   * @author 团队名
   * @date 2026-02-27
   */
  ```
- 函数头部：说明功能、参数含义、返回值含义、注意事项；
  ```c
  /**
   * @brief 建立TCP连接
   * @param port 目标端口号（1-65535）
   * @param ip 目标IP地址（字符串，如"127.0.0.1"）
   * @return 成功返回连接fd，失败返回-1（-2=IP非法，-3=端口非法）
   * @note 调用前需确保网络已初始化
   */
  int net_tcp_connect(const char *ip, int port);
  ```
- 复杂逻辑：说明设计思路、为什么这么写（而非写了什么）；
- 特殊处理：比如内存释放、错误处理、兼容逻辑；
- 常量/宏：说明含义（而非字面量）：`#define MAX_RETRY 3 // 最大重连次数`。

##### 3. 禁用注释
- 无意义注释：`// 加1` `// 循环`；
- 过时注释：代码修改后未同步更新的注释；
- 重复注释：注释内容与代码完全一致。

#### 七、编译与调试规范
1. 编译选项：
   - 开启所有警告：`gcc -Wall -Wextra -Werror`（将警告视为错误，杜绝潜在问题）；
   - 指定C标准：`-std=c99`/`-std=c11`（团队统一）；
   - 开启调试信息：`-g`（便于gdb调试），发布版本加`-O2`（优化）；
2. 调试：
   - 禁止用`printf`调试后残留（用日志库替代）；
   - 调试代码加`#ifdef DEBUG`包裹，发布版本关闭；
3. 版本控制：
   - 禁止提交临时调试代码、无用注释；
   - 提交信息规范：`[模块名] 功能/修复：具体描述`（如`[net] 修复TCP重连时的内存泄漏`）。

---

#### 八、通用禁忌
1. 禁止使用`goto`（除非是错误处理的统一跳转，如资源释放）；
2. 禁止使用`gets()`（缓冲区溢出风险），用`fgets()`替代；
3. 禁止硬编码：所有魔法数（如1024、8080）改为宏定义；
4. 禁止全局函数重载（C语言不支持，易冲突）；
5. 禁止跨模块直接修改全局变量（通过接口函数操作）。

### 总结
这份规范覆盖了C语言团队协作的核心维度，关键要点：
1. **一致性**：命名、格式、注释的统一是团队协作的基础，建议配合Clang-Format等工具自动化落地；
2. **安全性**：指针判空、内存配对释放、初始化是C语言的核心底线；
3. **可读性**：注释说明“为什么”，命名见名知意，函数单一职责；
4. **工程化**：合理的目录/文件结构，头文件保护，编译选项严格化。

### 落地建议
1. 团队内投票确认规范细节（如缩进空格数、行长度），形成《团队C语言编码规范文档》；
2. 用工具强制约束：Clang-Format（格式）、Lint工具（语法检查）；
3. 代码Review时重点检查规范执行情况；
4. 新人入职先学习规范，写Demo通过规范检查后再参与开发。

### 嵌入式C语言团队协作编程规范（工业级）
#### 一、核心原则（嵌入式专属补充）
1. **资源优先**：代码必须轻量化，杜绝内存/Flash浪费（嵌入式设备通常KB级RAM、MB级Flash）；
2. **实时性保障**：中断/任务执行时间可控，禁止耗时操作（如无限循环、大内存拷贝）；
3. **硬件安全**：严格遵循外设/寄存器操作规范，避免硬件损坏；
4. **可移植性**：硬件相关代码与业务代码解耦，便于适配不同芯片；
5. **鲁棒性**：应对电压波动、外设异常、通信丢包等极端场景。

#### 二、工程结构规范（嵌入式专属）
嵌入式工程核心是“分层设计”，避免硬件与业务耦合，目录结构示例（适配RTOS/裸机）：
```
project/
├── bsp/              # 板级支持包（BSP）：硬件底层，与芯片强相关
│   ├── stm32f103/    # 芯片型号（如STM32F103）
│   │   ├── gpio/     # 外设驱动（GPIO）
│   │   ├── uart/     # 外设驱动（UART）
│   │   ├── timer/    # 外设驱动（定时器）
│   │   └── bsp.h     # BSP公共头文件
├── driver/           # 设备驱动：与硬件解耦的通用驱动（如传感器、模组）
│   ├── ds18b20/      # 温度传感器驱动
│   ├── sim800c/      # 4G模组驱动
├── app/              # 应用层：业务逻辑（与硬件无关）
│   ├── task/         # 任务模块（RTOS）/ 功能模块（裸机）
│   ├── protocol/     # 通信协议（如Modbus、MQTT）
├── os/               # RTOS相关（如FreeRTOS、RT-Thread）
│   ├── config/       # RTOS配置
│   ├── port/         # RTOS移植层
├── config/           # 全局配置（宏定义、参数）
│   ├── sys_config.h  # 系统配置（如时钟频率、引脚定义）
│   ├── user_config.h # 用户配置（如业务参数）
├── utils/            # 工具函数（通用、无依赖）
│   ├── crc.c/h       # CRC校验
│   ├── mem.c/h       # 内存管理（适配嵌入式的轻量版）
├── main.c            # 程序入口（初始化+任务创建）
├── Makefile/MDK工程  # 编译脚本/IDE工程文件
└── doc/              # 文档（硬件手册、驱动说明、调试日志）
```

##### 分层职责边界（核心！）
| 层级       | 职责                                  | 禁止操作                          |
|------------|---------------------------------------|-----------------------------------|
| BSP层      | 寄存器操作、外设底层初始化（如GPIO模式配置） | 业务逻辑、RTOS调用、耗时操作      |
| Driver层   | 外设/模组的通用接口（如DS18B20读温度）| 直接操作寄存器、跨层调用业务代码  |
| App层      | 业务逻辑（如数据采集、上报）| 直接操作寄存器、修改硬件配置      |
| Utils层    | 通用工具函数（CRC、字符串处理）| 依赖硬件、依赖RTOS                |

#### 三、命名规范（嵌入式专属补充）
在通用命名规则基础上，强化硬件相关命名的可读性：
| 类型                | 命名规则（嵌入式专属）| 示例                                  |
|---------------------|---------------------------------------|---------------------------------------|
| 寄存器/引脚         | 芯片前缀_外设_功能_编号（全大写）| `STM32_GPIOA_PIN5` `STM32_UART1_BAUDRATE` |
| 中断函数            | isr_外设_功能（小写+下划线）| `isr_uart1_rx()` `isr_timer3_overflow()` |
| BSP函数             | bsp_外设_操作（小写+下划线）| `bsp_gpio_set_mode()` `bsp_uart_send()` |
| 驱动函数            | drv_设备名_操作（小写+下划线）| `drv_ds18b20_read_temp()` `drv_sim800c_send_at()` |
| RTOS任务            | task_模块名_功能（小写+下划线）|
