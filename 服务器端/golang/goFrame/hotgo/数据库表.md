### 说明：JWT Token 存储策略
该系统采用**无状态 JWT 方案**：
- **Token 不存储在数据库中**，而是通过签名算法验证合法性
- 用户认证时，从 `hg_admin_member` 表验证用户名密码，成功后生成 JWT
- Token 包含用户 ID、角色等信息，服务端通过解密验证身份

# HotGo项目数据库设计概述

此 SQL Dump 来自 HotGo 框架（基于 Vue + goframe2.0 的全栈开发平台）。HotGo 集成了 JWT 认证和 Casbin 权限控制。数据库表划分为多个模块：**管理员管理**（`hg_admin_*`）、**系统配置**（`hg_sys_*`）、**插件扩展**（`hg_addon_*`）、**支付模块**（`hg_pay_*`）等。其中与权限管理（RBAC）及登录认证（JWT）相关的核心表包括用户表、角色表、菜单权限表以及 Casbin 策略表等。HotGo采用基于角色的访问控制（RBAC, role-based access control）模型，即通过角色关联用户并向角色分配权限。接下来详细分析 RBAC 相关的表结构及 JWT 认证流程。

## 用户、角色与权限（RBAC）结构

- **`hg_admin_member`（管理员用户表）**：存储系统管理员/用户信息，包括 `id`（用户ID）、`username`（用户名）、`password_hash`（密码哈希）、`salt`（密码盐）等验证字段，以及`real_name`、`email`、`mobile`等联系信息。还包括组织结构字段如 `dept_id`（部门ID）、`pid`/`level`/`tree`（层级关系）用于树形组织架构和上级管理关系。`role_id` 字段默认为 10，可为用户指定主角色。表中还记录了多租户（`tenant_id`）、状态（`status`）、创建/更新时间等信息。**安全建议**：`password_hash` 字段使用的是固定长度哈希（如 MD5），建议改为现代哈希算法（如 Argon2、bcrypt 等）并配合随机盐；这样即使数据库泄漏，攻击者离线破解难度显著增加。
- **`hg_admin_role`（角色表）**：定义系统角色，包括 `id`、`name`（角色名）、`key`（角色标识字符串，如 `admin`）、`data_scope`（数据范围控制）、`custom_dept`（自定义部门权限）、`pid`/`level`/`tree`（角色继承层级）等字段。每个角色可对应一套权限配置，`status` 指示角色是否启用。该表将角色组织成树结构，支持角色继承和层级权限分配。
- **`hg_admin_menu`（菜单权限表）**：存储系统菜单和权限项。包括 `id`、`pid`（父菜单ID）、`title`（菜单标题）、`name`（路由名称编码）、`path`（路由地址）、`icon`、`type`（类型：1 目录/2 菜单/3 按钮）、`permissions`（权限字符串集合），以及用于前端路由的 `component`、`redirect` 等字段。`permissions` 或 `permission_name` 字段通常用于标识后端接口的权限点，以实现接口级权限控制。菜单表中还包含了 `always_show`、`keep_alive`、`hidden`、`affix` 等显示与缓存控制字段，以及排序和状态字段。该表在前端用于动态构造可访问的菜单和路由，同时为 Casbin 权限校验提供资源（即“对象”）。
- **`hg_admin_member_role`（用户-角色关联表）**：关联用户与角色，每条记录含 `member_id`（用户ID）和 `role_id`（角色ID），主键为二者组合。通过该表，一个用户可以关联多个角色，实现多角色授权。
- **`hg_admin_role_menu`（角色-菜单关联表）**：关联角色与菜单权限，每条记录含 `role_id` 和 `menu_id`，表示某角色对某菜单/权限项拥有访问权。通过该表，可以灵活地为角色分配哪些菜单/权限，从而控制不同角色的功能可见性与操作权限。
- **`hg_admin_role_casbin`（Casbin 策略表）**：存储 Casbin 访问控制策略规则。中指出 Casbin 默认将策略存储为表 `(id, ptype, v0, v1, v2, v3, v4, v5)`。此表结构与之对应：`id` 为主键，`p_type`（ptype）表明规则类型（如“p” 表示权限规则，“g” 表示角色继承规则等），`v0`~`v5` 字段分别存储策略中的主体（subject）、对象（object）、动作（action）等部分，具体数量和含义视 Casbin 模型配置而定。应用启动时，系统会从此表加载所有策略规则到 Casbin 引擎中，用于后续请求的权限校验。举例来说，一条规则可能是 `(p, role_admin, /api/user, GET)`, 表示角色 `role_admin` 可以对 `/api/user` 接口执行 GET 操作。Casbin 引擎会缓存角色继承关系和权限树，以优化查找速度。  
- **`hg_admin_post`（岗位表）**及**`hg_admin_member_post`（用户-岗位关联表）**：用于管理“岗位”概念（职务），类似角色管理，但通常用于描述组织内部职位层次，与系统功能权限本身关联较小。本项目中岗位表含 `id`、`code`、`name`、`sort` 等字段。`hg_admin_member_post` 表记录管理员与岗位之间的关联（复合主键为成员ID+岗位ID）。岗位通常用于组织架构或职位授权，不同于功能权限（RBAC）模型，但仍属于用户身份的一部分。

以上表格和关联实现了典型的 **RBAC 权限模型**：用户可有多个角色，角色可有多个权限（菜单），权限以资源+动作的形式由 Casbin 策略表具体定义。请求到达时，系统根据用户所属角色查找对应的 Casbin 策略，判断该角色是否有权限访问当前接口。

## JWT 认证设计与流程

HotGo 使用 JWT（JSON Web Token）进行用户身份认证。典型流程如下：  
1. **登录认证**：前端发送用户名/密码等凭证，后端在 `hg_admin_member` 表中查找用户并验证密码（使用存储的 `password_hash` 和 `salt`）。密码校验通过后，后端生成一个 JWT 令牌，该令牌内通常包含用户 ID、角色信息或租户 ID 等，以及到期时间。  
2. **返回并缓存令牌**：生成的 JWT 返回给前端（通常在 HTTP 响应头或响应体中）。同时，应用将该令牌记录在 Redis 缓存中，用于会话管理和单点登录控制（即限制一个用户只允许在有限数量的终端同时登录）。HotGo 官方说明提到：“使用 Redis 记录当前活动用户的 JWT 令牌并实现多终端登录限制”。  
3. **后续请求校验**：前端在后续 API 请求中携带 JWT（通常放在 Authorization 头）。后端中间件首先验证 JWT 的签名和有效性（如签名正确、未过期等），然后检查该令牌是否在 Redis 中存在（若启用多端登录限制，一旦某用户多端登录旧令牌可被删除）。验证成功后，从令牌或数据库中加载用户身份和角色。  
4. **权限授权**：在 JWT 验证通过后，系统进一步执行 RBAC 授权。Casbin 引擎根据当前用户的角色和请求的资源（通常是请求路径+HTTP 方法）查找 `hg_admin_role_casbin` 中的规则，判断是否允许访问。如通过，则继续执行业务逻辑；否则返回 403 权限不足。  

总结：JWT 提供了无状态的认证凭证（只在必要时记录在 Redis 中以便会话控制），Casbin 提供了细粒度的权限控制逻辑。整个登录和授权流程确保只有经过认证的用户才能访问接口，且只有具备相应角色/权限的用户才能访问特定资源。

## 执行逻辑与数据流

- **登录阶段**：用户提交登录信息 → 后端查 `hg_admin_member` 验证身份 → 成功后生成 JWT（含用户ID和角色/租户信息）→ 将 JWT 返回给前端并存入 Redis 缓存。
- **请求处理阶段**：每次请求时，后端中间件首先从 HTTP 请求头中取出 JWT，并使用预先约定的密钥验证签名和有效期（建议令牌有效期不要过长）。验证通过后，系统根据令牌中携带的用户ID，查找 `hg_admin_member` 确认用户状态，并加载用户所属的角色列表（可以从数据库或令牌中）。  
- **权限校验阶段（Casbin 引擎）**：使用 Casbin 引擎加载 `hg_admin_role_casbin` 中的规则，根据当前用户的角色身份（`subject`）与请求的资源/动作（`object/action`）匹配策略。如果匹配到允许规则则放行，否则拒绝访问。此步骤通常发生在控制器层之前，确保未授权请求被拦截。在动态路由场景下，`hg_admin_menu.permissions` 字段也可用于辅助前端菜单筛选和路由守卫，但核心授权仍依赖 Casbin 策略。  
- **日志与审计**：系统中还包含日志表（如 `hg_sys_log`、`hg_sys_login_log`）记录请求详情和登录事件，可用于审计和监控。每次登录会在 `hg_sys_login_log` 插入一条记录，方便追踪登录失败/成功情况。  

通过上述流程，系统实现了“先认证后授权”的机制：认证阶段使用 JWT 验证身份，授权阶段使用 Casbin 的 RBAC 规则判断资源访问权限。

## 安全建议

- **加强密码存储安全**：尽管数据库中存在 `salt` 字段，但当前使用的 `password_hash` 字段长度为 32，暗示可能使用了 MD5 或类似算法。建议采用业界推荐的现代哈希算法（如 Argon2id、bcrypt 或 PBKDF2）。例如，OWASP 建议新系统优先使用 Argon2id（或 scrypt），传统系统至少使用 bcrypt 并设置足够高的工作因子。合理的盐和慢哈希能够显著降低暴力破解风险。  
- **限制令牌有效期**：JWT 在带来无状态便利的同时，如果过长有效期被截获则风险较高。建议设置较短的过期时间（如数小时），并使用刷新机制延长会话。正如安全专家指出：“任何 JWT/cookie 有效期越长，被攻击者利用的时间越多”，因此可将 JWT 令牌寿命控制在 5 小时以内。同时结合 Redis 缓存及时清除过期或登出用户的令牌。  
- **使用 HTTPS 和安全配置**：确保前后端通信使用 HTTPS，以防令牌在传输过程中被窃取。配置 JWT 签名密钥（SecretKey）在环境变量或配置文件中妥善保护，不要硬编码在源码或数据库中。可考虑为不同租户/应用使用独立签名密钥。  
- **最小权限原则**：在 RBAC 设计中，避免给角色过多权限。仅分配角色实际需要的菜单和接口权限。对于 `data_scope` 等数据范围字段，应精细配置，确保不同用户仅能访问授权的数据范围。Casbin 策略表中可以按需精简规则集，减少授权决策的开销和误授风险。  
- **日志与监控**：利用 `hg_sys_log`、`hg_sys_login_log` 等表记录和审计用户行为，及时发现异常操作（如多次失败登录、非法访问尝试等）。必要时可将敏感操作（如密码修改、权限变更）进行二次验证或多因素认证加强安全。  
- **定期更新依赖**：保持 Casbin、JWT 库和框架组件更新到最新版本，以修补已知安全漏洞。如有自定义 Casbin 模型或策略，更改时应重新加载策略（Casbin 支持热加载策略），避免配置不同步造成漏洞。

通过以上措施，可在现有数据库结构基础上，进一步强化 JWT 与 RBAC 的安全和可靠性，提升系统整体的安全防护能力。
