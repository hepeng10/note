# 结构
* 数据库（Database）：数据库是 PostgreSQL 中的最高层次的结构，用于组织和管理数据。一个 PostgreSQL 实例可以包含多个数据库，每个数据库都有自己的数据文件和配置。数据库是用户访问和操作数据的主要入口。
* 模式（Schema）：模式是数据库中的一个逻辑容器，用于组织和管理数据库中的表、视图、函数等对象。每个数据库可以包含多个模式（默认为 public），每个模式都有自己的命名空间和权限。（将不同的表放在不同的模式中，实现更进一步的分组和权限管理）
* 表（Table）：表是数据库中的基本存储单元，用于存储和管理数据。每个表都有固定的结构，包括列和行。列定义了表的字段和数据类型，行存储了实际的数据记录。表是用户查询和操作数据的主要对象。

**与MySQL的区别是多了模式这个概念。比如多租户大项目中，可以把每个租户的数据放在不同的模式中，实现数据隔离和权限管理。**

# 表结构
## 核心数据类型
PostgreSQL 以其丰富的数据类型著称，以下是开发中最常用的几类：

### 数值类型
- INTEGER/INT: 4 字节整数，范围约±21 亿。
- BIGINT: 8 字节整数，用于大 ID 或大数据量计数。
- NUMERIC(p, s)/DECIMAL: 精确的小数，用于金额。p是总位数，s 是小数点后的位数。
- SERIAL/BIGSERIAL: 自增整数（实际上是封装了SEQUENCE）。

### 字符类型
- VARCHAR(n): 变长字符串，有长度限制。
- TEXT: 变长字符串，无长度限制（PostgreSQL 推荐直接用这个，除非有业务硬性长度约束）。
- CHAR(n): 定长字符串，不足部分补空格。

### 日期/时间类型
- TIMESTAMP: 日期和时间。
- TIMESTAMPTZ: 带时区的日期和时间（生产环境推荐使用，避免时区混乱）。
- DATE: 仅日期。
- INTERVAL: 时间间隔（如1 day 2 hours）。
- tsrange: 对应timestamp without time zone 的范围。
- tstzrange: 对应timestamp with time zone的范围（推荐用于跨时区业务）。
- daterange: 对应date 的范围。

### 特色/高级类型
这些类型都比较实用。
- BOOLEAN: TRUE, FALSE, 或NULL。
- JSONB: 二进制存储的 JSON 数据，支持索引，性能极佳。（存储JSON数据后，可以通过JSON数据中的字段进行查询等操作）
- UUID: 通用唯一识别码。
- ARRAY: 数组类型，例如TEXT[] 可以存储标签列表。
- INET：ip类型

#### JSONB
JSONB用于直接存储JSON数据，为什么不将JSON数据转换为多个字段存储呢？因为有些数据不是固定的，比如物联网设备中有些型号会上传湿度，有些则不会，如果每个字段都建一个列，那么表结构就会非常臃肿，而且这些列中会有很多空值。使用JSONB可以直接存储这些不固定的数据，并且通过索引和查询功能来访问这些数据。

## 列约束
约束用于确保数据的准确性和可靠性。
|约束类型|描述|示例|
|---|---|---|
|NOT NULL|强制列不能包含NULL 值。|	name TEXT NOT NULL|
|UNIQUE|确保列中的所有值互不相同。|	email TEXT UNIQUE|
|PRIMARY KEY|主键，唯一标识每一行。隐含NOT NULL和UNIQUE。|	id SERIAL PRIMARY KEY|
|FOREIGN KEY|外键，建立表与表之间的链接，防止破坏关系。|	user_id INT REFERENCES users(id)|
|CHECK|检查值是否满足特定逻辑条件。|	age INT CHECK (age >= 18)|
|DEFAULT|如果插入时未指定值，则使用默认值。|	created_at TIMESTAMPTZ DEFAULT NOW()|

# 数据库操作
## 创建数据库
使用 navicat 连接到 PostgreSQL 后，右键新建数据库，输入数据库名称后点确定，会自动默认设置所有者、编码这些。然后为了安全，可以先点击上方的角色，创建一个新的角色，设置好权限后，再编辑数据库，把这个角色设置为数据库的所有者。

## 查询
- 模糊查询：
    - like：模糊查询，区分大小写。`WHERE name LIKE 'John%';`
    - ilike：模糊查询，不区分大小写。`WHERE name ILIKE '%john%';`
- extract：提取日期时间中的部分，如年、月、日等。`WHERE EXTRACT(YEAR FROM created_at) = 2026;`
- 数组查询：
    - 单条件包含：`WHERE 'tag1' = ANY(tags);` 这条语句会返回所有包含 'tag1' 的记录。（使用 = 运算符和数组 ANY 函数）
    - 同时包含：`WHERE tags @> ARRAY['tag1', 'tag2'];` 这条语句会返回所有包含 'tag1' 和 'tag2' 的记录。（使用 @> 运算符和 ARRAY）
    - 包含任一：`WHERE tags && ARRAY['tag1', 'tag2'];` 这条语句会返回所有包含 'tag1' 或 'tag2' 的记录。（使用 && 运算符和 ARRAY）
- JSONB查询：
    - 直接查询：`WHERE data->>'field' = 'value';` 这条语句会返回所有 data 字段中 field 字段值为 'value' 的记录。（使用 ->> 运算符取出的值是字符串类型，即使JSON中的值是数字类型，也会被转换为字符串）
        `WHERE (metadata->'video'->'resolution'->>'width')::int = 1920;`可以这样转换为整数类型进行比较。
    - 嵌套查询：`WHERE data->'field1'->>'field2' = 'value';` 这条语句会返回所有 data 字段中 field1 字段下的 field2 字段值为 'value' 的记录。（使用 -> 运算符取出的值是 JSONB 类型，可以继续使用 ->> 取出字符串值）
    - 字段是否存在：`WHERE data ? 'field';` 这条语句会返回所有 data 字段中存在 field 字段的记录。（使用 ? 运算符检查字段是否存在）
- 网络地址查询：
    - 精确查询：`WHERE ip_address = '192.168.1.1';` 这条语句会返回所有 ip_address 字段值为 '192.168.1.1' 的记录。（使用 INET 运算符和字符串值进行比较）
    - 范围查询：`WHERE ip_address << '192.168.1.0/24';` 这条语句会返回所有 ip_address 字段值在 '192.168.1.0/24' 范围内的记录。（使用 << 运算符和字符串值进行比较）
- 聚合统计：`SELECT department, COUNT(*) AS employee_count FROM employees GROUP BY department;` 这条语句会返回每个部门的员工数量。（使用 GROUP BY 运算符按 department 字段分组，COUNT(*) 函数计算每个分组的记录数）

# 常用函数
## 字符串处理函数
当文件路径、用户名格式不统一时，这些函数能帮大忙。
- CONCAT(a, b)/||：拼接字符串，CONCAT 比 || 更好，会自动忽略 NULL 值。
    `SELECT CONCAT(first_name, ' ', last_name, ' (ID:', employee_id, ')') AS full_info FROM employees;`，将多个字段查询结果拼接为一个字符串。
- UPPER(a)：将字符串转换为大写。
    `SELECT UPPER(name) from users`，返回 name 字段的所有值转换为大写。
- LOWER(a)：将字符串转换为小写。
    `SELECT LOWER(email) from users`，返回 email 字段的所有值转换为小写。
- SUBSTR(string, start, len)：截取字符串。
    `SELECT SUBSTR(name, 1, 5) AS short_name FROM users;`，从 name 字段的值中截取前 5 个字符作为 short_name。
- REPLACE(string, from, to)：替换内容。
    `SELECT REPLACE(email, '@', 'at') AS email FROM users;`，将 email 字段的值中的 '@' 替换为 'at'。
- COALESCE(value, default)：【超级常用】 如果字段是 NULL，就给它一个默认值。
    `SELECT COALESCE(phone, 'N/A') AS phone FROM users;`，如果 phone 字段是 NULL，就返回 'N/A'。

## 数值计算函数
- ROUND(numeric, 2)：四舍五入，保留两位小数。
    `SELECT ROUND(3.1415926, 2) AS rounded;`，返回 3.14。
- CEIL()/FLOOR()：向上/向下取整。
    `SELECT CEIL(3.14) AS ceil_value, FLOOR(3.14) AS floor_value;`，返回 4 和 3。
- ABS()：取绝对值。
    `SELECT ABS(-10) AS absolute_value;`，返回 10。

## 日期时间函数
- NOW()：获取当前完整时间。
    `SELECT NOW() AS current_time;`，返回当前时间。
- CURRENT_DATE：获取当前日期。
    `SELECT CURRENT_DATE AS current_date;`，返回当前日期。
- AGE(timestamp)：计算时间差。
    `SELECT AGE('2026-01-01'::TIMESTAMPTZ) AS age;`，计算从 '2026-01-01' 到现在的时间差。
    `SELECT file_name, created_at, AGE(created_at) AS active_time FROM file_details;`，返回每个文件的创建时间created_at和从创建到现在的时间差active_time。
- EXTRACT(field FROM source)：提取年、月、日、小时。
    `SELECT EXTRACT(YEAR FROM '2026-01-01'::TIMESTAMPTZ) AS year;`，从字符串提取年份。
    `SELECT EXTRACT(MONTH FROM '2026-05-01'::TIMESTAMPTZ) AS month;`，从字符串提取月份。
    `SELECT EXTRACT(DAY FROM '2026-05-01'::TIMESTAMPTZ) AS day;`，从字符串提取日期。
    `SELECT EXTRACT(HOUR FROM created_at) AS hour, COUNT(*) AS file_count FROM file_details GROUP BY hour;`，从 created_at 字段中提取小时，统计每个小时的文件数量file_count。
- TO_CHAR()：将时间格式化为字符串。
    `SELECT TO_CHAR(NOW(), 'YYYY-MM-DD HH24:MI:SS') AS formatted_time;`，将当前时间格式化为 'YYYY-MM-DD HH24:MI:SS' 的字符串。
    `SELECT TO_CHAR(created_at, 'YYYY-MM-DD HH24:MI:SS') FROM file_details;`，将 created_at 字段格式化为 'YYYY-MM-DD HH24:MI:SS' 的字符串。

## 流程控制与聚合函数
- CASE WHEN：SQL 里的if-else。（一般不在SQL里搞这样的查询）
    ```sql
    -- 给文件分等级
    SELECT file_name,
        CASE
            WHEN file_size > 1024*1024*100 THEN '大文件'
            WHEN file_size > 1024*1024*10 THEN '中文件'
            ELSE '小文件'
            END AS file_level
    FROM files;
    ```
- STRING_AGG(field, delimiter)：【PG特色】 把多行结果合并成一行字符串。
    `SELECT uploader_ip, STRING_AGG(tags::text, ' | ') FROM file_details GROUP BY uploader_ip;`，将同一 uploader_ip 的 tags 字段值合并成一个字符串，使用 ' | ' 作为分隔符。
- COUNT()/SUM()/AVG()/MAX()/MIN()：统计数量、求和、平均值、最大值、最小值。
    `SELECT COUNT(*) AS total_count, SUM(file_size) AS total_size, AVG(file_size) AS avg_size, MAX(file_size) AS max_size, MIN(file_size) AS min_size FROM file_details;`，统计文件总数、总大小、平均大小、最大大小、最小大小。

# 表的关联
## 一对一
表 A 的一行只能对应表 B 的一行。通常用于将“核心高频数据”与“扩展低频数据”分离，提高查询效率
示例：用户 (Users) 与 用户详细信息 (User_Profiles)
在用户系统中，用户的账号密码是核心，而个人介绍、头像 URL、收货地址属于扩展信息。
```sql
-- 主表：核心账户
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username TEXT NOT NULL UNIQUE
);

-- 扩展表：详细资料
CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY, -- 既是主键，也是外键
    avatar_url TEXT,
    bio TEXT,
    -- 定义外键约束，确保user_id在users表中存在，且删除时级联删除
    CONSTRAINT fk_user 
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```
实现要点：在子表中，将外键字段设为`PRIMARY KEY`或`UNIQUE`，确保一个用户 ID 只能在 Profile 表里出现一次。
`ON DELETE CASCADE`：定义“连坐”逻辑 ——最核心部分。
这是定义当 **主表（users）** 的数据被删除时，**从表（user_profiles）** 该怎么办。

- `CASCADE` **(级联)** ：就像多米诺骨牌。如果 ID 为 1 的用户被删除了，数据库会自动、静默地把`user_profiles`里所有`user_id = 1` 的行也删掉。
- 为什么用它：在“一对一”或“一对多”关系中，如果主体（用户）都不存在了，相关的详细资料或头像信息也就没有存在的意义了。使用级联可以防止数据库堆积垃圾数据。

除了`CASCADE`，你有时也会看到这些写法：
|选项|效果|适用场景
|--|--|--|
|`RESTRICT` (默认)|	如果用户还有资料，就不准删这个用户。|	保护重要数据，防止误删。
|`SET NULL`|	用户删了，资料表里的user_id变成NULL。|	用户注销了，但你想保留他的评论或痕迹。
|`NO ACTION`|	与 RESTRICT 类似，但在事务结束时检查。|	复杂的事务处理。

### 插入数据
```sql
-- 第一步：插入核心用户
-- 我们利用 RETURNING 直接获取系统生成的自增 ID
INSERT INTO users (username) 
VALUES ('fengfeng') 
RETURNING id; 

-- 假设上面返回的 ID 是 1
-- 第二步：插入对应的详细资料
INSERT INTO user_profiles (user_id, avatar_url, bio) 
VALUES (1, 'https://example.com/avatar.png', '技术教育者，B站UP主');

-- 尝试再次为 ID 为 1 的用户插入资料（会报错！）
-- 报错信息：duplicate key value violates unique constraint "user_profiles_pkey"
-- 这正是我们设计成 PRIMARY KEY 的目的，保证了一对一的严格性。
```

### 查询数据
正向联查和反向联查：
```sql
-- 内连接：只返回在两个表中都存在关联记录的行
SELECT username, avatar_url
FROM users
JOIN user_profiles up ON users.id = up.user_id;

-- 左连接：保留主表 users 的所有行，即使没有对应的 user_profiles
SELECT username, avatar_url
FROM users
LEFT JOIN user_profiles up ON users.id = up.user_id;

-- 反向左连接（右连接的语义）: 保留 user_profiles 的所有行
SELECT avatar_url, username
FROM user_profiles
LEFT JOIN users u ON u.id = user_profiles.user_id;
```

#### JOIN
`JOIN` / `INNER JOIN`：只保留两边都有匹配的记录。适合“一对一”关系中，只想查询同时存在主表和扩展表的数据时使用。

`LEFT JOIN`：保留左表所有记录，右表缺失时结果为 NULL。适合想查询所有用户，并附带可选的扩展资料的场景。

`RIGHT JOIN`：保留右表所有记录，左表缺失时结果为 NULL。在 PostgreSQL 中，通常用左连接换位实现，写法更直观。

`FULL JOIN`：保留两边所有记录，任一端缺失时对应列为 NULL。用于需要“主表和扩展表都要出现”的全量对比场景。

一对一关系查询常见思路：
- 主表为主体时，`LEFT JOIN` 可以保证所有主体行都返回。
- 如果只关心“既有用户又有资料”的记录，使用 `INNER JOIN`。
- 如果想验证哪些用户缺少资料，`LEFT JOIN` + `WHERE up.user_id IS NULL`。

```sql
-- 找出没有资料的用户
SELECT u.id, u.username
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE up.user_id IS NULL;
```
### 删除数据
设置`CASCADE`之后，删除用户之后，关联的用户详情也会删除

## 一对多
表 A 的一行可以对应表 B 的多行。通常用于表示“主体与多个相关记录”的关系。

示例：博客文章 (Posts) 与 评论 (Comments)
```sql
CREATE TABLE posts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    author TEXT NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 查询与 GROUP BY 用法
在一对多关系中，常常需要按“主体”聚合从表的数据，这时可以使用 `GROUP BY`：

```sql
-- 统计每篇文章的评论数量
SELECT p.id,
       p.title,
       COUNT(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title
ORDER BY comment_count DESC;
```

`GROUP BY` 主要作用是把多个评论行聚合成每篇文章一条结果，常用场景包括：
- 统计关联行数（如评论数、订单数）
- 求和/平均/最大值（如评论字数总和、订单金额总和）
- 按主体汇总从表字段值

### 其它常见查询
```sql
-- 查询每篇文章最新一条评论时间
SELECT p.id,
       p.title,
       MAX(c.created_at) AS last_comment_at
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title;
```

如果只想查询某篇文章的所有评论，则不用 `GROUP BY`，直接按外键过滤即可：
```sql
SELECT *
FROM comments
WHERE post_id = 123
ORDER BY created_at;
```

## 多对多
多对多关系表示一条记录可以关联对方表中的多条记录，反之亦然。
典型示例：文章 (Posts) 与 标签 (Tags)，一个文章可以有多个标签，一个标签也可以属于多篇文章。

### 中间表（关联表）
多对多必须通过中间表来实现。中间表通常只存放两端的外键，有时还会携带关系属性，例如关联时间、排序、状态等。

```sql
CREATE TABLE posts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL
);

CREATE TABLE tags (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE post_tags (
    post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    tag_id BIGINT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (post_id, tag_id) -- 联合主键，确保每个文章-标签对只出现一次
);
```

### 联合主键与唯一约束
`post_tags` 的主键通常由两个外键组成，这称为联合主键。它保证了同一对 `post_id` 和 `tag_id` 只能出现一次，从而防止重复关联。

如果中间表有额外 ID 字段，也应对 `post_id, tag_id` 添加唯一索引，以同样防止重复：
```sql
CREATE TABLE post_tags (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    tag_id BIGINT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (post_id, tag_id) -- 唯一约束，确保每个文章-标签对只出现一次
);
```

### 查询示例
```sql
-- 查询某篇文章的标签
SELECT t.id, t.name
FROM tags t
JOIN post_tags pt ON t.id = pt.tag_id
WHERE pt.post_id = 123;

-- 查询某个标签关联的文章
SELECT p.id, p.title
FROM posts p
JOIN post_tags pt ON p.id = pt.post_id
WHERE pt.tag_id = 456;

-- 查询文章及其标签（按文章聚合标签）
SELECT p.id,
       p.title,
       STRING_AGG(t.name, ', ') AS tag_list
FROM posts p
LEFT JOIN post_tags pt ON p.id = pt.post_id -- 先关联中间表
LEFT JOIN tags t ON t.id = pt.tag_id -- 再通过中间表的标签 ID关联标签表
GROUP BY p.id, p.title; -- 按文章 ID 和标题分组，确保每个文章只出现一次
```

### 要点总结
- 多对多关系必须通过中间表拆成两段一对多关系。
- 中间表的联合主键 `PRIMARY KEY (a_id, b_id)` 是最常见且最严格的设计，确保关联唯一。
- 如果需要在关联上存储额外属性，可以在中间表加字段，而仍然保留联合主键或唯一约束。
- 关系查询通常通过两个 `JOIN` 实现：从一端表到中间表，再到另一端表。

# 索引
索引是数据库中用于加速查询的一种数据结构。它类似于书籍的目录，可以帮助数据库快速定位到满足条件的数据行，而不需要扫描整个表。
- 没有索引时，数据库必须从第一行开始，扫描表中的每一行，直到找到所有符合条件的行。这在数据量很大时会非常慢。
- 有索引后，数据库可以根据索引快速定位到符合条件的行（类似于书籍的目录），而不需要扫描整个表。
- Primary Key, Unique 会自动创建索引，不再需要手动添加索引；而 Foreign Key 在 pgsql 中不会自动创建索引，在 mysql 中会自动创建索引。

## 索引类型
- B-tree 索引：默认索引类型，适用于大多数查询场景
- Hash 索引：适用于等值查询，但不支持范围查询。
- GIN 索引：适用于包含数组、JSONB等复杂数据类型的字段。
- GiST 索引：适用于地理空间数据和全文搜索等特殊场景。
- BRIN 索引：适用于大表中具有物理相关性的字段，如时间戳。
- Bitmap 索引：适用于布尔值字段，如已读状态。
- Partial 索引：适用于部分查询条件的字段，如 `WHERE age > 18`。
- Expression 索引：适用于计算结果的字段，如 `LOWER(email)`。

## 索引使用建议
- 频繁查询的字段应该创建索引，尤其是 WHERE 条件中的字段。
- 联结（JOIN）和排序（ORDER BY）中使用的字段也应该考虑创建索引。
- 不要过度索引，过多的索引会增加写入操作的开销，如插入、更新、删除等。
- 定期维护索引，如重建索引（REINDEX）和分析表（ANALYZE），以保持查询性能。
- 对于大表，考虑使用分区表和分区索引来提高查询性能。
- 使用 `EXPLAIN` 和 `EXPLAIN ANALYZE` 来分析查询计划，了解索引是否被正确使用，以及查询的性能瓶颈在哪里。
    如：`EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com'`;
- 对于 JSONB 类型的字段，使用 GIN 索引可以显著提高查询性能。

## 索引维护
- 定期检查索引的使用情况，删除不再需要的索引。
- 对于频繁更新的表，考虑使用部分索引或表达式索引，以减少索引维护的开销。
- 使用 `REINDEX` 命令重建索引，以解决索引碎片片化问题。
- 使用 `ANALYZE` 命令更新统计信息，以帮助查询优化器选择最优的执行计划。

## 索引示例
### 创建索引
```sql
-- 1. 基础B-tree索引：最常用，用于等值和范围查询
-- idx_users_email 是索引名称，可以随便取，但通常使用 idx 表示
CREATE INDEX idx_users_email ON users(email); -- 默认使用 B-tree 索引
CREATE INDEX idx_users_email ON users USING btree(email); -- 显示指定 B-tree 索引

-- 2. 唯一索引：常用，确保字段值唯一，适合用于业务唯一键（如用户名）
CREATE UNIQUE INDEX idx_users_username ON users(username);

-- 3. 复合索引：常用，优化多个字段组合查询
-- 适合频繁按组织和状态联合查询员工的场景
CREATE INDEX idx_employees_org_status ON employees(organization_id, status);

-- 4. 部分索引：常用且非常实用，特别适合软删除、状态字段等场景
-- 场景：只想快速查询活跃用户，对注销用户不关心
CREATE INDEX idx_users_active ON users(id) WHERE is_active = true;

-- 5. 表达式索引：常用，优化函数计算结果查询
-- 场景：经常按邮箱的小写版本查询
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

-- 6. 多列唯一索引：常用，用于保证组合唯一性
-- 场景：确保同一用户在同一项目中只有一条记录
CREATE UNIQUE INDEX idx_assignments_unique ON user_projects(user_id, project_id);

-- 7. 部分唯一索引：常用场景，确保在特定条件下唯一
-- 场景：已删除的数据不参与唯一性约束，允许多个软删除记录
CREATE UNIQUE INDEX idx_users_email_active ON users(email) WHERE deleted_at IS NULL;

-- 8. GIN索引：较常用于 JSONB/数组查询
-- 场景：物联网设备上传的JSON传感器数据，需要快速按字段查询
CREATE INDEX idx_devices_metadata_gin ON devices USING GIN(metadata);

-- 9. 数组字段索引：较常用于数组查询，适合 tags TEXT[] 类型
-- 场景：标签表中需要快速查询包含特定标签的记录
CREATE INDEX idx_posts_tags_gin ON posts USING GIN(tags);

-- 10. BRIN索引：适合大表顺序数据，不是日常必用，但非常适合时间序列场景
-- 场景：日志表有数百万条记录，created_at 是物理有序的
CREATE INDEX idx_logs_created_at_brin ON logs USING BRIN(created_at);

-- 11. GiST索引：专用，主要用于地理空间或全文搜索等特殊场景
-- 场景：查询距离某点一定范围内的位置数据
CREATE INDEX idx_locations_geo ON locations USING GiST(geom);

-- 12. Hash索引：不常用，PostgreSQL 默认B-tree已足够，大多数场景可以不用
-- 场景：极少数大量等值查询，可做测试，但谨慎使用
CREATE INDEX idx_orders_user_hash ON orders USING HASH(user_id);
```


### 查询与管理索引
```sql
-- 查看表的所有索引
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'users';

-- 查看索引的使用情况（多少次被扫描）
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;

-- 查找未被使用的索引（可以考虑删除）
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- 查看索引占用的磁盘空间
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) as index_size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;

-- 使用 EXPLAIN 分析查询是否使用了索引
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'test@example.com';

-- 重建索引（解决索引碎片化）
REINDEX INDEX idx_users_email;

-- 重建表上的所有索引
REINDEX TABLE users;

-- 更新表的统计信息（帮助查询优化器选择最优计划）
ANALYZE users;

-- 删除不需要的索引
DROP INDEX IF EXISTS idx_users_old_index;
```

## 索引的“代价”：
天下没有免费的午餐，索引虽好，但不能全表所有字段都加。每一条索引都会带来以下开销：
- **磁盘空间**： 索引本身是一棵树，需要占用额外的存储空间。
- **写入性能**：当你执行**INSERT、UPDATE或DELETE**时，数据库不仅要改数据，还要同步更新索引树。索引越多，写操作越慢。
- **维护成本**：随着数据频繁变动，索引可能会产生碎片，偶尔需要REINDEX（重建索引）来恢复性能。

### 这些情况下索引会“失效”
很多新手加了索引发现查询还是慢，通常是因为触发了索引失效：

|场景	|错误示例 (会导致 Seq Scan)|正确姿势|
|--|--|--|
|模糊查询	|WHERE file_name LIKE '%file_999%';	|只有“左前缀”匹配file_999% 才能用索引|
|函数操作	|WHERE UPPER(file_name) = 'FILE.PDF';	|建立函数索引或在查询前处理数据|
|类型不匹配	|WHERE id = '123'; (id是数字，却传字符串)	|保持类型一致，避免隐式转换|
|最左匹配	|复合索引(a, b)只查b	|复合索引必须从最左侧字段开始匹配|

# 事务与锁
## 事务
用最通俗的话说，事务就是：“要么全做完，要么一点都不做，绝不允许停在半路。”
场景：用户花 100 元买 VIP。如果钱扣了，结果数据库断电了，会员没加上。

### 核心语法
```sql
BEGIN; -- 开启事务
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE members SET vip = true WHERE user_id = 1;
COMMIT; -- 提交事务
```

如果中间出错，应该回滚：
```sql
ROLLBACK; -- 撤销本次事务中的所有修改
```

### 事务特点（ACID）
- 原子性（Atomicity）：一组操作要么全部成功，要么全部回滚。
- 一致性（Consistency）：事务前后，数据库保持合法状态。
- 隔离性（Isolation）：事务互相隔离，避免读到中间状态。
- 持久性（Durability）：事务提交后，结果不会丢失。

### 隔离级别（常用）
- READ COMMITTED：默认级别，避免读到未提交数据。最常用。
- REPEATABLE READ：同一事务内重复读取结果一致，避免“不可重复读”。
- SERIALIZABLE：最高级别，完全串行化，性能开销大。

设置隔离级别：
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

### 保存点（Savepoint）
```sql
BEGIN;
SAVEPOINT before_update;
UPDATE ...;
ROLLBACK TO SAVEPOINT before_update; -- 只回滚到保存点
COMMIT;
```

### 流程简析
```sql
BEGIN;             -- 开启事务
UPDATE ...;        -- 执行业务逻辑
SAVEPOINT my_sp;   -- (可选) 设置保存点，类似于单机游戏的存档
UPDATE ...;
ROLLBACK TO my_sp; -- (可选) 发现错了，回滚到存档点
COMMIT;            -- 提交，所有改动生效
```

## 锁
在 PostgreSQL 中，锁是确保数据库并发安全（Consistency & Isolation）的核心机制。简单来说，它防止了多个用户同时修改同一条数据而导致的混乱。
PostgreSQL 默认使用行级锁，尽量减少冲突。锁是保证事务隔离的关键。

### 常见锁类型
- 行锁（Row Lock）：最常见，SQL 语句自动加锁，例如 `UPDATE`、`DELETE`。
- 表锁（Table Lock）：少用，通常为 `LOCK TABLE`。修改表结构的时候通常会自动加锁。
- 意向锁：内部自动管理，告诉数据库行锁方向，不需要手动处理。
- 建议锁：这是 PostgreSQL 的一大特色。它不是由数据库引擎自动加的，而是由程序员定义的一种逻辑锁。
    - 适用于分布式系统中跨数据库的锁协调；MQTT设备控制（同一设备不能同时升级）等。
    - 通过 `pg_advisory_lock` 和 `pg_advisory_unlock` 来使用。
    - 锁定一个整数 ID，适合锁定业务对象（如订单 ID）而不是数据库行。

### 典型用法
```sql
BEGIN;
-- 锁定要更新的行，避免其他事务修改
SELECT * FROM orders WHERE id = 123 FOR UPDATE;
COMMIT;
```
使用 FOR UPDATE 会在查询的行上加一个写锁，其他事务如果也想修改这行数据，就必须等这个事务提交或回滚后才能继续。
使用 FOR UPDATE 加锁后，其它连接可以对此行进行读取操作，但是不能进行写和删除操作。

### 读锁 vs 写锁
- `SELECT ... FOR SHARE`：读取时锁定行，允许其他事务共享读取，但禁止修改。
- `SELECT ... FOR UPDATE`：获取写锁，禁止其他事务更新或删除该行。

### 死锁与避免
死锁：两个事务互相等待对方释放锁，都会阻塞。
PostgreSQL 会自动检测并回滚其中一个事务。

避免方法：
- 按固定顺序访问表和行
- 尽量缩短事务时间
- 避免在事务中做大量计算或等待用户输入

### 快速使用建议
- 只在必要时显式开启事务，默认单条语句也是事务。
- 读操作尽量不加锁，避免影响并发。
- 更新前先 `SELECT ... FOR UPDATE`，确保后续修改安全。
- 事务内不要执行 `COMMIT` 之外的外部调用（如 HTTP 请求）。

### 简易场景总结
- 支付场景：`BEGIN` → 修改余额 → 修改订单状态 → `COMMIT`
- 写入前检查：`SELECT ... FOR UPDATE` → 校验 → `UPDATE` → `COMMIT`
- 若失败：`ROLLBACK`

**虽然数据库自身有锁机制，但是在业务上仍然需要考虑并发问题，需要手动使用事务和锁来确保数据一致性。**

### 示例
```sql
BEGIN;
-- 锁定 id 为 100 的行，别人必须等我处理完
SELECT * FROM products WHERE id = 100 FOR UPDATE; -- FOR UPDATE 会加写锁，其他事务无法修改这行数据

UPDATE products SET stock = stock - 1 WHERE id = 100;
COMMIT;
```
更现代的方法：原子更新
```sql
UPDATE products
SET stock = stock - 1
WHERE id=1
AND stock > 0; -- stock 大于0时才会更新
```
由于是原子操作，所以不存在并发问题，且性能更好。

# 注意事项
- 外键：一般业务里面都会去掉外键，使用逻辑外键。外键会影响性能，如果数据量大了，分表后外键也会出现问题，所以一般不使用外键约束，而是通过代码来保证数据的完整性和一致性。
- 联表查询：联表查询也和外键有类似的问题，分库分表后会出现问题。（如果确定不会分库分表之类，使用联表查询性能上、安全性上会更好）

# 视图和CTE
## 视图（View）
- 定义：把查询保存为一个可复用的虚拟表。视图本身不存数据（普通视图）。
- 语法示例：
```sql
CREATE VIEW active_users AS
SELECT id, username, email FROM users WHERE is_active = true;
-- 使用视图：
SELECT * FROM active_users WHERE email ILIKE '%@example.com';
```
- 物化视图（Materialized View）：保存查询结果到表，适用于复杂/耗时查询。
```sql
CREATE MATERIALIZED VIEW mv_daily_report AS
SELECT date_trunc('day', created_at) AS day, COUNT(*) AS cnt
FROM events GROUP BY day;

-- 刷新物化视图
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_report; -- 在线刷新（需要唯一索引）

-- 可对物化视图建索引
CREATE INDEX ON mv_daily_report(day);
```

注意：普通视图便于封装和权限管理，但不会提高性能；需要缓存结果时考虑物化视图并定期刷新。

## CTE（WITH，公共表表达式）
- 定义：在单个查询中定义临时命名结果集，增强可读性并复用子查询。
- 基本用法：
```sql
-- 未使用 CTE
SELECT customer_id, COUNT(*)
FROM (
    SELECT * FROM orders WHERE created_at > now() - interval '7 days'
) AS recent
GROUP BY customer_id;

-- 使用 CTE
WITH recent AS (
    SELECT * FROM orders WHERE created_at > now() - interval '7 days'
) -- 注意：这里没有分号
SELECT customer_id, COUNT(*) FROM recent GROUP BY customer_id;
```

- 递归CTE（处理树/层级）示例：
```sql
WITH RECURSIVE subordinates AS (
    SELECT id, manager_id, name FROM employees WHERE id = 1
    UNION ALL
    SELECT e.id, e.manager_id, e.name
    FROM employees e
    JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;
```
- 在更新/插入中使用 CTE（返回受影响行）：
```sql
WITH moved AS (
    UPDATE products SET stock = stock - 1
    WHERE id = 100 AND stock > 0
    RETURNING *
)
SELECT * FROM moved; -- 查看刚修改的行
```

### 性能与注意事项
- PostgreSQL 12 及以上会对非递归 CTE 进行内联优化（不再默认物化），若需要强制物化或不物化可以使用 `MATERIALIZED` / `NOT MATERIALIZED` 提示：
```sql
WITH cte AS MATERIALIZED (...) -- 强制物化（早期行为）
WITH cte AS NOT MATERIALIZED (...) -- 强制内联
```
- CTE 适合提高可读性、避免重复子查询或实现递归；但在数据量大或不当使用时可能增加临时开销，应结合 `EXPLAIN` 评估。


## 视图 vs CTE：怎么选？

|特性|CTE (WITH)|视图 (View)|
|--|--|--|
|生命周期|只在当前这条 SQL 里有效|永久保存在数据库里|
|类比|局部变量|全局公共函数|
|适用场景|仅仅为了让这一行长查询变好看|经常要用的复杂查询、报表统计|
|权限控制|无|非常强大（可以给用户看视图，但不给他看原表）|

# 用户与角色
一般建议一个项目一个数据库，一个数据库一个角色。这样权限管理更清晰，安全性更高。
角色（Role）：PostgreSQL 中的用户和组统称为角色。用户可加入角色，类似RBAC。

## 创建角色和用户
```sql
-- 1. 创建一个角色
CREATE ROLE managers; 

-- 2. 创建一个用户
CREATE USER fengfeng WITH PASSWORD 'fengfeng';

-- 3. 让“用户”加入“角色”
GRANT managers TO fengfeng;
```
现在这个用户，可以登录，可以看到有哪些库，有哪些表，但是不能创建库，创建表，查询表数据。

## 权限管理
给用户设置某一个库的只读权限：
```sql
-- 1. 创建用户
CREATE USER reader_user WITH PASSWORD 'fengfeng';

-- 2. 基础进门权
GRANT CONNECT ON DATABASE db TO reader_user;  -- 可以进入db这个库
GRANT USAGE ON SCHEMA public TO reader_user; -- 可以进入public这个模式

-- 3. 核心只读权（现在的表 + 序列）
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reader_user;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO reader_user;

-- 4. 自动化（未来的表）
ALTER DEFAULT PRIVILEGES IN SCHEMA public 
GRANT SELECT ON TABLES TO reader_user;
```

给用户设置一个库的增删改查权限：
```sql
CREATE USER feng_app WITH PASSWORD 'fengfeng';

GRANT CONNECT ON DATABASE fengfeng_db TO feng_app;
GRANT USAGE ON SCHEMA public TO feng_app;

-- 1. 针对表：赋予全部增删改查权限
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO feng_app;

-- 2. 针对序列：必须给权限！否则无法执行自增 ID 的插入
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA public TO feng_app;

-- 后续新创建的表也拥有权限
ALTER DEFAULT PRIVILEGES IN SCHEMA public 
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO feng_app;

ALTER DEFAULT PRIVILEGES IN SCHEMA public 
GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO feng_app;
```

# 备份与恢复
在 PostgreSQL 中，备份主要分为两种：逻辑备份（导出的 SQL 文件，易读、跨版本好用）和物理备份（直接拷贝底层文件，快但不易读）。

## pg_dump单库备份
### 备份
pg_dump是一个命令行工具，它会把数据库里的表结构、数据、序列、权限等全部变成一段长长的 SQL 脚本。
```bash
# 格式：pg_dump -U [用户名] -d [数据库名] > [备份文件名.sql]
pg_dump -U postgres -d db > db_0414.sql

# 备份为压缩的二进制格式（压缩后会小很多）
pg_dump -U postgres -F c -d db > db_0414.bak
```
- -U: 指定用户名（通常用超级用户 postgres）。
- -t: 只备份某张表（例如：-t cloud_files）。
- -n: 只备份某个模式（例如：-n storage）。
- -F: 指定格式。-Fc 会生成自定义二进制压缩格式，体积更小，且支持并行恢复（推荐！）。

### 恢复
恢复的方式取决于你备份时的格式。
**恢复纯文本 SQL 备份**
如果备份的是.sql文件，直接用psql 运行它即可：(注意：这个库要先创建好！)
```bash
# 格式：psql -U [用户名] -d [目标数据库] < [备份文件]
psql -U postgres -d db1 < db_0414.sql
```

**恢复二进制备份 (pg_restore)**
如果用了-Fc压缩格式，必须用专属的 pg_restore 工具：

- -c 代表先清理（删除）旧表再恢复，防止冲突。

## 全文搜索
以前要实现全文搜索需要使用 ES。

PostgreSQL 自带全文搜索能力，结合 `tsvector`/`tsquery` 和扩展 `pg_trgm` 可以实现高效搜索。

### 内置全文搜索
```sql
CREATE INDEX idx_articles_content ON articles USING GIN(to_tsvector('simple', content));

-- 2. 查询示例
SELECT id, title
FROM articles
WHERE to_tsvector('simple', content) @@ to_tsquery('simple', 'postgres & 扩展');
```

- `to_tsvector('simple', content)`：把文本切词并标准化为向量。`to_tsvector` 会把文本分词、可选去停用词、进行词干化等处理，生成一个 `tsvector` 类型的值。

- `to_tsquery('simple', 'postgres & 扩展')`：构造查询条件，`&` 表示“且”，`|` 表示“或”，`!` 表示“非”。
    - `simple`：使用最简单的分词器，按空白切词，不做英语词干或停用词过滤（适合保留原词，中文可用）。
    - `english`：英语分词，包含停用词和词干化，适合英文内容。
    - `french`, `german`, `spanish`, `italian`, `russian` 等：Postgres 自带多语言配置，分别针对各语言的停用词与词干算法。
    推荐：英文内容优先用 `english`；中文建议使用 `zhparser`（或先用外部分词器预分词后存入 `tsvector`）。
- `@@`：文本向量与查询条件匹配。

### 结合 `unaccent` 处理中文或带重音字符
```sql
CREATE EXTENSION IF NOT EXISTS unaccent;
SELECT id, title
FROM articles
WHERE to_tsvector('simple', unaccent(content)) @@ to_tsquery('simple', unaccent('全文 & 搜索'));
```

### 预分词
上面的查询是在查询时才做分词，数据量大或并发高时会非常慢。常见优化是“预分词”（把 `tsvector` 预先计算并存储），常见实现方式：

```sql
-- 生成列示例（Postgres 12+）
ALTER TABLE articles ADD COLUMN content_tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('english', coalesce(content,''))) STORED;

CREATE INDEX idx_articles_content_tsv ON articles USING GIN(content_tsv);
```

- 为什么用预分词：
    - 查询时只做向量匹配，命中索引，响应快；
    - 写入会有额外成本（触发器或生成列），但通常可接受；

- 其它实践建议：
    - 若要去重/去掉重音：在触发器中使用 `unaccent()`：`to_tsvector('english', unaccent(coalesce(NEW.content,'')))`；
    - 对中文内容优先用 `zhparser` 或外部分词器先分词后存入 `tsvector`；
    - GIN 索引默认 `fastupdate = on`，对高写入场景可考虑调整或定期 `REINDEX`；
    - 定期执行 `ANALYZE`，确保统计信息准确，帮助查询优化器选择索引；
    - 大批量导入时先移除索引或关闭触发器，导入完成后重建索引以节省总开销。


### `pg_trgm`：适合模糊匹配和补全
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_articles_title_trgm ON articles USING GIN(title gin_trgm_ops);

SELECT id, title
FROM articles
WHERE title ILIKE '%Postgres%' -- 普通模糊
  OR title % 'Postgres'; -- pg_trgm 相似度匹配
```

### `zhparser`：中文全文搜索分词
`zhparser` 是一个针对中文的 PostgreSQL 分词扩展，适合在中文内容上构建更准确的 `tsvector`。

中文分词需要编译扩展，建议直接用对应的docker镜像：
```shell
# 这里推荐使用社区预集成好的镜像，省去手动编译的痛苦
docker pull zhparser/zhparser:alpine-16
docker run -d --name pg-chinese -p 5432:5432 -e POSTGRES_PASSWORD=root zhparser/zhparser:alpine-16
```

```sql
CREATE EXTENSION IF NOT EXISTS zhparser;
CREATE TEXT SEARCH CONFIGURATION chinese (PARSER = zhparser);
ALTER TEXT SEARCH CONFIGURATION chinese ADD MAPPING FOR n,v,a,i,e,l WITH simple;

-- 1. 生成中文分词 tsvector
SELECT to_tsvector('zhparser', '这是一个 PostgreSQL 中文全文搜索示例');

-- 2. 建索引
CREATE INDEX idx_articles_content_zh ON articles USING GIN(to_tsvector('zhparser', content));

-- 3. 查询
SELECT id, title
FROM articles
WHERE to_tsvector('zhparser', content) @@ to_tsquery('zhparser', 'PostgreSQL & 中文');
```

- `zhparser` 支持中文分词，并可与 PostgreSQL 原生全文搜索配合使用。
- 安装方式通常通过系统包管理器或源码编译：`CREATE EXTENSION zhparser;`。
- 若你的 PostgreSQL 环境不支持 `zhparser`，请先确认已安装对应的系统库（如 `postgresql-server-dev` / `postgresql-devel` 等）。

### 快速实战建议
- 需要关键词搜索时，优先用 `tsvector` + `tsquery`；它是 PG 原生全文搜索。
- 需要模糊搜索、拼写纠错、近似匹配时，补上 `pg_trgm`。
- 中文内容建议使用 `zhparser` 生成 `tsvector`，再建 `GIN` 索引。
- 建议在文本字段上建 `GIN` 索引：`to_tsvector(...)` 或 `gin_trgm_ops`。
- 注意：中文分词效果一般，复杂场景可以先做分词后存入 `tsvector`。

### 常见语法对比
```sql
-- 全文搜索：适合关键词匹配
SELECT * FROM articles
WHERE to_tsvector('simple', content) @@ to_tsquery('simple', '全文 & 搜索');

-- 三字母相似度：适合模糊匹配、补全
-- 比 LIKE 性能更好。LIKE 通常只适用于前后缀匹配和数据量小时使用
SELECT * FROM articles
WHERE title % 'Postgres';
```

## 地理位置
用于附近的人等业务。
在地理信息系统（GIS）领域，PostgreSQL的PostGIS插件是绝对的行业霸主。
如果只是计算两点之间的距离，可以用自带的earthdistance。
```sql
CREATE EXTENSION cube;          -- earthdistance 依赖它
CREATE EXTENSION earthdistance;
```
计算两点之间的距离：
```sql
-- 计算 (经度1, 纬度1) 到 (经度2, 纬度2) 的距离
SELECT earth_distance(
    ll_to_earth(23.45, 113.12), 
    ll_to_earth(23.50, 113.15)
) AS distance_meters;
```
